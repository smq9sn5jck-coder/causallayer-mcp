# Determinism proofs

This directory holds weekly reproductions of all 10 FaultKey demo scenarios
against the live MCP worker at `https://mcp.faultkey.com/mcp`.

Every Monday at 12:00 UTC, GitHub Actions runs
[`scripts/weekly-determinism.mjs`](../scripts/weekly-determinism.mjs) on a
fresh runner, generates `proofs/YYYY-MM-DD.json`, updates the table below,
and commits both back to `main`.

**Why this exists.** The FaultKey product claim is that the engine is
deterministic — given the same canonical input it must return the same
`request_hash` and `merkle_root` every time. The proofs in this directory
are the public, third-party-replicable evidence of that claim. Any reader
can clone the repo, run the script, and `diff` their JSON against the
committed file.

## Two determinism notions

The script tracks two distinct properties:

| Property | What it means | Spec guarantee? |
|---|---|---|
| **Canonical-input stable** | Same incident input → same `request_hash` + `merkle_root`. | **Yes**. This is what "deterministic" means in the FaultKey spec. |
| **Cert-id stable** | Same incident input → same `certificateId`. | **Stricter** than the spec. Engine v0.5.0-demo currently mixes a per-request nonce into the cert id, so this is `N` until that's pinned. Tracked as an open issue. |

The badge column ("Canonical-input stable") is the only one that maps to
the marketing claim. "Cert-id stable" is shown for transparency.

## Verifying these proofs yourself

```bash
git clone https://github.com/smq9sn5jck-coder/causallayer-mcp
cd causallayer-mcp
node scripts/weekly-determinism.mjs
# Then diff the just-written file against any committed proof:
diff <(jq -S '.scenarios | map({id, request_hash, merkle_root})' proofs/$(date +%F).json) \
     <(jq -S '.scenarios | map({id, request_hash, merkle_root})' proofs/<other-date>.json)
```

If your file's `request_hash` and `merkle_root` columns match the committed
file's, the engine is canonical-input deterministic for those scenarios.

If anything diverges, please open an issue — that's exactly the kind of
drift this log exists to catch.

## Rate limits

The public demo endpoint enforces a per-IP burst limit. The CI runner uses
GitHub-hosted IPs (which rotate per job), so the workflow does not hit the
limit in practice. If you're running the script locally and hit
`DEMO_RATE_LIMITED`, the script retries honouring `retry_after_seconds`;
you can also email `sales@causallayer.io` for a paid tenant with no
per-IP limits.
